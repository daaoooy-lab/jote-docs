## 배경

`tech-stack-selection.md`에서 미결로 남겨둔 임베딩 공급자를 결정함. Claude(Anthropic)는 채팅/생성 전용이라 임베딩 API를 제공하지 않으므로, 텍스트→벡터 변환을 전담할 별도 공급자가 필요함.

<br/><br/>

## 검토한 방식

### 관리형 API 서비스
- **OpenAI** (`text-embedding-3-small/large`) — 가장 대중적, 가격 저렴, 품질 안정적
- **Voyage AI** — Anthropic이 공식 추천/제휴하는 임베딩 전문 업체
- **Cohere Embed**, **Google (Vertex AI)**, **Jina AI** — 비슷한 포지션의 대안

API 호출로 텍스트를 보내면 벡터를 응답받는 방식. 서버 리소스 부담 없이 바로 사용 가능하나, 호출량만큼 비용이 발생하고 텍스트가 외부로 전송됨.

<br/>

### 오픈소스 자체 호스팅
- **BGE**, **E5**, **Nomic Embed**, **Sentence-Transformers(all-MiniLM 등)** — Hugging Face에서 받아 FastAPI 서비스 안에 직접 로드
- 경량 모델은 GPU 없이 CPU만으로도 동작 가능

API 비용은 없지만 AI 서비스 프로세스 안에서 직접 텍스트→벡터 변환을 수행.

<br/><br/>

## 비용 관점 검토

직관과 달리 개인 프로젝트 규모에서는 관리형 API가 총비용 기준으로 더 저렴함.

- **관리형 API**: OpenAI `text-embedding-3-small` 기준 1M 토큰당 $0.02. 개인 메모 앱 볼륨으로는 연간 비용이 1달러 안팎
- **자체 호스팅**: API 비용은 0원이지만, 임베딩 모델을 메모리에 올려야 해서 서버 RAM 사용량이 늘어남. Railway/Fly.io 무료 티어(RAM 512MB~1GB)를 초과해 유료 플랜 업그레이드가 필요해질 수 있어, 오히려 인프라 비용이 API 비용보다 커질 가능성이 있음

<br/><br/>

## 현업 경험 관점 검토

- 실제로 AI 기능을 제품에 붙이는 회사 대부분은 임베딩 모델을 직접 서빙하지 않고 관리형 API를 사용함. 자체 모델 서빙은 MLOps/ML 인프라 전담 영역이라 일반 백엔드/AI 제품 엔지니어에게 기대되는 역량이 아님
- 채용 시장 기준으로도 "RAG 파이프라인 설계", "벡터 DB 연동", "LLM API 오케스트레이션"이 Applied AI Engineer의 핵심 역량으로 언급되고, 임베딩 모델 자체 호스팅은 더 특수한 ML Infra 트랙에 가까움
- Jote의 목표("AI Agent/LLM 기반 기능 **구현** 경험")는 제품에 AI를 통합하는 경험이지, ML 모델을 직접 운영하는 경험이 아니므로 관리형 API 쪽이 목표와 더 부합함

<br/><br/>

## 결정

**관리형 API(OpenAI 또는 Voyage AI)**를 임베딩 공급자로 확정함. 비용과 현업 경험 관점 모두에서 자체 호스팅보다 우위에 있다고 판단.
