## 아키텍처 관점 분류

브레인스토밍한 기능들을 "나중에 바꾸기 어려운 것"과 "나중에 확장으로 붙이기 쉬운 것"으로 구분.

### 초반부터 잡고 가야 하는 것
- 리치 텍스트 에디터 선택 + 콘텐츠 저장 포맷 (Markdown vs JSON) — 이후 AI 작성 지원 기능 전체가 이 위에서 동작
- 자동 저장 방식 (API 설계, 저장 시점/충돌 처리) — 백엔드 API 계약과 직결
- 의미 기반 검색 / 임베딩 인프라 — AI 메모 관리, AI Agent 전체의 토대
- 멀티 디바이스 동기화 / 실시간 공동 편집 (하게 된다면) — 동시성 모델을 처음부터 설계해야 함

<br/>

### 나중에 확장으로 붙이기 쉬운 것
- AI 작성 지원 대부분 (제목/태그 자동생성, 요약, 문장 다듬기, 번역, 이어쓰기 등) — 선택 텍스트에 LLM 호출 후 결과 삽입하는 독립적인 패턴
- 음성 메모 텍스트화, OCR — 별도 입력 파이프라인이라 기존 구조에 영향 없음
- AI 메모 관리 / AI Agent 나머지 기능 — 임베딩 인프라만 있으면 하나씩 얹는 방식으로 확장 가능
- 정리/검색(비-AI), 생산성/개인화, 외부 연동, 첨부/체크리스트/코드블록 — 표준 CRUD 확장 또는 UI 레이어
- 메모 잠금, 공개/비공개 설정 — 접근 제어 레이어라 나중에 붙여도 무방
- 버전 히스토리 — 스냅샷 저장을 새로 추가하고 그 시점부터 기록하면 되므로, 과거 마이그레이션 없이 나중에 추가 가능

<br/><br/>

## 버전 히스토리 / 종단간 암호화 검토

### 버전 히스토리
스냅샷 테이블만 추가하면 되고 과거 데이터 마이그레이션이 필요 없어 나중에 추가하기 어렵지 않음. MVP에는 불필요, 여유 생기면 추가하는 후순위 기능으로 결정.

<br/>

### 종단간 암호화
E2E 암호화는 서비스 운영자조차 내용을 볼 수 없게 하는 것이 핵심(DB 유출 대비, 신뢰 확보 등의 장점). 하지만 Jote의 AI 기능(요약, 임베딩 기반 검색, AI Agent)은 서버/AI가 메모 내용을 읽어야 동작하므로 근본적으로 충돌함. 진짜 E2E로 가려면 AI 처리를 전부 클라이언트에서 직접 호출해야 하는데, 이는 "프론트/백엔드/AI 분리 아키텍처 경험"이라는 프로젝트 목표와도 맞지 않음. **제외**하기로 결정. 프라이버시가 필요하면 저장 시 암호화(encryption at rest) 정도로 대체.

<br/><br/>

## MoSCoW 우선순위

### Must have
- 메모 작성 / 수정 / 삭제
- 리치 텍스트 에디터 + Markdown 지원
- 자동 저장
- 의미 기반(자연어) 검색
- 내 메모 기반 AI 채팅

<br/>

### Should have
- 메모 요약
- 태그 자동 생성
- 관련 메모 추천
- 메모 자동 분류 / 카테고리 추천
- 체크리스트, 코드 블록
- 키워드 전체 검색
- 이미지 첨부
- 즐겨찾기/고정, 폴더 구조
- 다크모드/테마

<br/>

### Could have
- 문장 다듬기, 맞춤법 교정, 번역, 이어쓰기
- 음성 메모 텍스트화, OCR 자동 요약
- 중복 탐지, 유사 메모 병합 제안, 지식 그래프, 자동 링크, 오래된 메모 재발견
- AI Agent 확장 (주제 정리, 통합 요약, 질문 답변, 실행 계획 생성, TODO 추출)
- 파일 첨부, 필터링, 최근 열어본 메모, 휴지통
- 단축키 커스터마이징, 오늘의 메모 대시보드, 습관 트래커
- 메모 잠금, 공개/비공개 설정, 메모 링크 공유
- Export/Import, 메모 통계, 버전 히스토리
- 오프라인 모드(PWA), 캘린더 연동, Markdown/PDF export, 개발자용 API 공개

<br/>

### Won't have
- 종단간 암호화
- 멀티 디바이스 동기화, 실시간 공동 편집, 댓글
- 크로스 플랫폼(모바일 네이티브) — 웹으로 한정
- Notion/Evernote 마이그레이션, 웹 클리퍼
